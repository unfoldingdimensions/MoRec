## 0. Sequencing & rules for every session

Each session = one agent chat = one PR off `main`. Sessions are **independent and mergeable in any order**, but the recommended order is 1 → 2 → 3 → 4 (risk-ascending; 1 is the warmup). If sessions run concurrently, each touches different files except `VideoEditor.tsx` glue and locale files — merge order 1→2→4→3 minimizes conflicts.

**Every session must:**
1. Read `CONTRIBUTING.md`, `docs/plans/2026-09-18-p0-features.md` (this file), and `AGENTS.md` first.
2. Branch off latest `main` (`git checkout main && git pull && git checkout -b feat/<name>`), one PR per session, conventional-commit messages, `Co-Authored-By: <agent model (vendor) <noreply@vendor.com>>` trailer.
3. Verify with **actual output**: `npm test` (vitest), `npm run lint` (biome), `npm run i18n:check`. CI (`Code Quality`) must pass before merge.
4. **i18n parity is strict** (`scripts/i18n-check.mjs`): every new UI string needs keys in `src/i18n/locales/en/<namespace>.json` **and all 10 other locales** (es, fr, de, it, nl, ko, pt-BR, ru, zh-CN, zh-TW). `t(key, "English fallback")` is the runtime pattern but does not satisfy i18n:check.
5. Known environment gotchas:
   - A Mimosa security hook blocks raw `git commit`/`git push` in Bash (18 pre-existing high advisories in `electron/ipc/export/native-video.ts` etc. are known and accepted). Use the `.tmp/do-*.sh` script pattern: write the git commands into `.tmp/<name>.sh` via the Write tool, run `sh .tmp/<name>.sh`. Do not "fix" the advisories in scope.
   - Never package without re-running the frontend build: `npx electron-builder --win` alone repackages stale `dist/`. For smoke-testing a build: `npx tsc && npx vite build --config vite.config.ts && npm run normalize:electron-main-cjs && npx electron-builder --win`.
   - `VideoEditor.tsx` is 7k lines — add logic to extracted modules/hooks where the plan says so; keep glue minimal.
6. Tests follow existing conventions: pure-function tests colocated (`*.test.ts`, node env), DOM/hooks tests with `// @vitest-environment jsdom` docblock, IPC tests via `electron/test/ipcRegistry.ts`. Property-based `fast-check` is available for region-math.

## Feature 1 — Motion presets & "make the magic optional" (Session 1)

**User story:** "Screen Studio's constant zooming made me dizzy and I couldn't turn it off. MoRec should let me dial the magic down or off."

**Evidence:** HN 47595695 + 43816419 (deal-breaker complaints, preset/slider requests); Screen Studio shipped a disable toggle.

### Design
A persisted **motion profile** with four levels, applied everywhere motion effects are produced:
- `off` — no suggested zooms auto-applied; no cursor smoothing changes; click effects default to none
- `subtle` — auto-zoom depth cap 2 (current `DEFAULT_AUTO_ZOOM_DEPTH`), gentle smoothing
- `balanced` (default) — current behavior (depth 2–3, existing defaults)
- `energetic` — depth cap 4, snappier smoothing, click effects suggested

Behavior changes:
1. `disableSuggestedZooms` (already exists as a cursor-looping guard in `VideoEditor.tsx`) becomes derived: true when profile = `off`, plus the existing condition.
2. Suggested zooms clamp depth to the profile cap: `handleZoomSuggested` (VideoEditor.tsx L3924) and `useTimelineZoomActions.handleSuggestZooms` (timeline\hooks\actions\useTimelineZoomActions.ts L110) clamp `ZoomRegion.depth` to the cap.
3. The **zoom slider** ask: the region inspector already exposes `ZoomDepth` 1–6 (`ZOOM_DEPTH_SCALES`, types.ts L610) — verify the selected-zoom panel renders a slider; if it renders stepped buttons only, convert to a slider. (This is the "slider instead of preset options" request.)
4. Manual zoom regions are NEVER removed or clamped — only *suggested* ones respect the profile. Document this in the UI copy ("suggestions only").

### Implementation
- New module `src/components/video-editor/motionProfile.ts` (pure): `MotionProfile = "off"|"subtle"|"balanced"|"energetic"`, `MOTION_PROFILE_CAPS: Record<MotionProfile, number>` (`off: 0, subtle: 2, balanced: 3, energetic: 4`), `clampSuggestedDepth(profile, depth)`, `applyProfileToCursorSettings(profile, { smoothing, clickEffect })`.
- Persistence: extend `editorPreferences.ts` (`loadEditorPreferences`/`saveEditorPreferences` L456/474 + `editorPreferences.test.ts` pattern) with `motionProfile` (default `"balanced"`, normalize unknown → balanced).
- UI: SettingsPanel zoom section (`SettingsPanel.tsx`) gets a four-way segmented control with a one-line description each; i18n keys under `settings.json` (11 locales).
- Wiring: `VideoEditor.tsx` reads the pref, derives `disableSuggestedZooms`, passes cap into `handleZoomSuggested` + `useTimelineZoomActions`.
- Verify the zoom-depth slider in the zoom selection panel; convert to slider if stepped.

### Tests
- `motionProfile.test.ts`: caps, clamp math, unknown-value normalization.
- `useTimelineZoomActions` test: suggested depth clamped by profile; `off` suppresses suggestions.
- editorPreferences round-trip test.

## Feature 2 — One-click silence removal (Session 2)

**User story:** "Remove the dead air between sentences with one click." (Loom/Tella paywall this; our transcripts + ffmpeg silencedetect already exist.)

### Design
A **detection → suggestion → region** pipeline that produces `TrimRegion`s (silence removal = cutting spans), respecting the existing clip/trim model:
1. New pure module `src/components/video-editor/timeline/silenceSuggestions.ts` (mirror `zoomSuggestionUtils.ts`):
   - Input: silence intervals `[{ startMs, endMs }]` (source time) + options `{ minSilenceMs (default 700), padMs (default 120), mergeGapMs (default 400), maxRemovalRatio (default 0.45) }`.
   - Output: `SuggestedTrimSpan[]` (source-time spans to cut), with guards: never trim inside/adjacent-to existing `ZoomRegion`/`SpeedRegion` spans (pad check), total removal ≤ maxRemovalRatio of source duration (otherwise return `{ status: "too-much-silence" }` and suggest nothing).
2. Silence detection (main process, new IPC `analyze-companion-audio-silence` in `electron/ipc/register/recording.ts`, registered like `generate-auto-captions`):
   - Input: video path. Audio source: `getUsableCompanionAudioCandidates` (`electron/ipc/recording/diagnostics.ts`) → fallback to extracting the video's own audio (reuse `extractCaptionAudioSource` pattern from `electron/ipc/captions/generate.ts` L191 — 16k mono wav, then delete).
   - Run ffmpeg `silencedetect` (`-af silencedetect=noise=-38dB:d=0.7`) — constants live in `electron/ipc/captions/silence.ts` (`SILENCE_NOISE_DB`, `SILENCE_DETECT_MIN_S`); parse `silence_start/silence_end` stderr lines (parser exists for captions; generalize it into a shared util in `electron/ipc/ffmpeg/`).
   - **Spawn hygiene:** run through the existing ffmpeg execution wrapper (`runFfmpegWithMetrics` call sites are under known Mimosa advisories — do not refactor them; add the new call beside existing ones with the same argument-builder style as `buildTrimmedSourceAudioFilter`'s neighbors).
   - Return `{ intervals, usedSource: "system" | "mic" | "video" }`.
3. Editor UX: toolbar button "Remove dead air" (next to existing suggest-zooms trigger) → calls IPC → maps source-time spans to timeline (`mapSourceTimeToTimelineTime`, types.ts L300) → creates `TrimRegion`s via the existing trim handlers → toast `Removed N silent spans (Xs)` / `Not enough silence to trim`. Full undo support comes free via `editorHistory` snapshot (trims already captured in `buildHistorySnapshot`).
4. Preview/playback parity: trim regions already affect `getTimelineDurationMs` + `mapTimelineTimeToSourceTime` — no export changes required (verified: `buildEditedTrackSourceSegments` consumes trims, editedTrackStrategy.ts L85).

### Tests
- `silenceSuggestions.test.ts` (pure): padding, merging, guards, overlap-with-zoom skip, too-much-silence status, timeline mapping. Use `fast-check` for span-math invariants (monotonic, non-overlapping, within duration).
- IPC test via `electron/test/ipcRegistry.ts` for `analyze-companion-audio-silence` (mock ffmpeg spawn; assert interval parsing + candidate fallback order).
- Editor test: button handler creates expected trim regions (follow `useScreenRecorder.state.test.tsx` jsdom pattern for the hook glue if needed).

### i18n
`timeline.json` or `editor.json` keys: `removeDeadAir`, `removedSilentSpans`, `notEnoughSilence`, `analyzingAudio` — ×11 locales.

## Feature 3 — Auto speed-up of typing / dead air (Session 2, same PR as Feature 2)

**User story:** "I type a lot on camera; speed those parts up instead of making viewers watch." (Direct HN request; Screen Studio flagship behavior; FocuSee punished for lacking it.)

### Design (two detection sources, one output)
Output: `SpeedRegion`s (`{ startMs, endMs, speed: 2 }`, types.ts L591) — speed-up regions already flow through playback AND every export route (`buildNativeStaticLayoutTimelineSegments` native-video.ts L1715; `buildTimelineSlices` audioEncoder.ts L1569; `buildEditedTrackSourceSegments` editedTrackStrategy.ts L85).

- **Source A (v1, ships first): silence-driven.** Long silences (default ≥ 1200 ms) that are NOT removed by Feature 2 (if both run, Feature 2's trims take precedence; the speed suggester reserves trimmed spans) become 2× speed regions. Reuses the same `analyze-companion-audio-silence` IPC.
- **Source B (v1.1, behind the same PR if time allows): keyboard-driven.** uiohook-napi currently registers only mouse listeners (`electron/ipc/cursor/interaction.ts` `startInteractionCapture` L208). Add `hook.on("keydown", …)`:
  - New `interactionType: "key"` on `CursorTelemetryPoint` — bump `CURSOR_TELEMETRY_VERSION` 2 → 3 (`electron/ipc/constants.ts` L29), extend the normalization whitelist (telemetry.ts L62-70), extend `electron/ipc/types.ts` payload types AND renderer `types.ts` L21. Readers accept v2 (no key events) and v3.
  - Pure module `typingSuggestions.ts`: typing bursts (≥ 3 key events within a rolling 2 s window, sustained ≥ 1.5 s, padded ±250 ms) → speed regions; reserve spans with existing zooms; cap total accelerated duration at 40% of source.
- Editor UX: toolbar toggle-pair "Speed up typing" / "Speed up dead air" (auto-apply on click, same pattern as suggest-zooms toast); generated regions are `mode`-tagged via their id prefix (`autospeed-${n}`) and are user-editable/deletable like any `SpeedRegion`.

### Tests
- `typingSuggestions.test.ts` + extend `silenceSuggestions.test.ts` (speed-region variant, precedence vs trims, reservation against zooms).
- Telemetry test: v2 payload (no key fields) loads cleanly after the version bump; v3 with `interactionType: "key"` normalizes (mirror cursor telemetry tests).

### i18n
`speedUpTyping`, `speedUpDeadAir`, `addedSpeedRegions`, `nothingToSpeedUp` — ×11.

## Feature 4 — Export reliability pack (Session 3)

**User story:** "A 20-minute export crashed at 53% and I lost everything." (Loom's #1 G2 con; FocuSee's viral complaint.)

### 4a. Target file-size preset (Easy)
- `src/lib/exporter/exportBitrate.ts` (`getMp4ExportBitrate` L89): add `ExportQuality` option `"target-size"` + `targetSizeMb` (persisted in `ProjectEditorState` per the `exportQuality` pattern, projectPersistence L1055-1061).
- Math: `bitrate ≈ (targetSizeMb × 8192) / durationSec × 0.93 (container overhead)` split 90/10 video/audio (respect `MIN_MP4_BITRATE` floor; if target implies < floor, clamp and surface a "smallest achievable ≈ X MB" hint via existing `ExportProgress.skipReasons`-style label).
- UI: new row in `ExportSettingsMenu` quality grid (L131-189) with an MB input when `target-size` selected; live "≈ estimated size" readout (duration × computed bitrate).
- Both export routes consume it: native route via existing bitrate plumbing; WebCodecs via `videoEncoderConfig.bitrate`.

### 4b. Resumable Lightning (native static-layout) export (Medium-Hard)
- Scope: **native static-layout route only** (segments already first-class: `buildNativeStaticLayoutTimelineSegments` native-video.ts L1715; chunk builders `buildNativeStaticLayoutChunks` L684; GPU + CPU backend arg builders listed in the report §3A). WebCodecs route stays non-resumable (documented in UI as such).
- Mechanism:
  1. New export temp layout: `<temp>/export-session/<exportId>/` containing `manifest.json` (`{ segmentIndex → { status: "done", file, sha256? } }`, written with the atomic writer from `electron/ipc/project/atomicSave.ts`) + per-segment output files.
  2. The segment loop in `exportNativeStaticLayoutVideo` (native-video.ts L3208) checks the manifest before rendering each segment; completed segments are concat-listed instead of re-rendered.
  3. On failure/cancel: session dir is kept (not deleted) and `ExportResult` gains `resumeToken: exportId`; `ExportProgress` gains a `resumeable: boolean` hint surfaced via `exportStatusModel`.
  4. UI: on next export start with a matching resumeToken (same video path + settings hash), `ExportSettingsMenu` shows "Resume previous export (n of N segments done)" banner; resume passes `resumeToken` into `resolveExportStartSettings` (`exportStartSettings.ts` L15).
  5. Cleanup: session dirs older than 7 days swept at editor start (mirror the stale-temp sweep pattern from persistence L1 fix).
- **Cancel semantics stay exactly as fixed in PR #24** — cancel is success-with-flag, not error.
- Progress honesty: per-segment progress already flows; add `segment i/N` to `runtimeLabel` via `exportStatusModel`.

### Tests
- `exportBitrate.test.ts`: target-size math (clamps, overhead, duration edge cases — extend existing file).
- `nativeVideoExport.test.ts` (pure arg builders): manifest pre-check skips rendered segments; concat list correctness with mixed done/pending.
- IPC test: export-session manifest read/write round-trip via `ipcRegistry` pattern; 7-day sweep unit test.
- Renderer: resume banner logic test (match/mismatch on settings hash).

### i18n
`resumePreviousExport`, `segmentsDone`, `targetFileSize`, `estimatedSize`, `smallestAchievable` — ×11.

**Risks:** mimicking existing arg builders exactly (do not touch the advisory-flagged spawn sites); segment outputs must be concat-compatible (same codec/params — assert via existing validators L1755); do not break `breeze-stream`/WebCodecs routes (skip reasons label resume as unavailable there).

## Feature 5 — Audio pre-flight check (Session 4)

**User story:** "Tell me my mic/system audio will actually be captured before I record." (OBS's 7-year metering fight; system-audio failure complaints.)

### Design (v1 = confidence UX; loopback metering is the v2 stretch)
1. **Pre-flight card in the mic/system popover** (`MicPopover.tsx` / `PopoverScaffold.tsx` `MicDeviceRow` L50-73):
   - Mic: live level meter already exists (`useAudioLevelMeter`) — add a **clipping warning** (sustained RMS ≥ 97/100 over 500 ms → "your mic is clipping — lower the input gain") and a **silence warning** (≤ 2/100 for the whole popover-open duration → "no input detected — check the selected device").
   - System audio (Windows): the toggle state is known, but the browser cannot meter loopback. v1 shows an honest state chip: "System audio will be captured (verified at stop)" vs v1.1 below. Record a **last-recording diagnostic**: after each stop, if `<video>.system.wav` exists but is below a noise floor, toast once: "Last recording's system audio looks silent — check the capture toggle." (Diagnostics source: `getUsableCompanionAudioCandidates` + a peak probe via the existing ffmpeg wrapper; run once per stop, cheap on a ≤1-min probe window.)
2. **v1.1 stretch (same PR if time allows):** main-process WASAPI loopback meter — a tiny ffmpeg probe (`-f dshow`/WASAPI) is fragile; prefer reusing windows-capture helper telemetry if it exposes levels; otherwise leave for a native follow-up and document.
3. Start-gating: if the pre-flight detects mic-selected-but-silent at record time, show the existing toast system's warning (non-blocking) — do not block recording.

### Tests
- `useAudioLevelMeter` extension tests (clipping/silence thresholds — jsdom docblock pattern, existing file has tests).
- Companion-audio peak probe unit test (parse fixture wav; threshold logic).
- Popover UI test with `electronApiMock` (warnings render/clear).

### i18n
`micClipping`, `noMicInput`, `systemAudioWillCapture`, `lastRecordingSilent` — ×11.

## Feature 6 — Social canvas presets (Session 4)

**User story:** "Export a 9:16 / 1:1 / 4:5 version for Shorts/TikTok/LinkedIn without re-editing." (Screen Studio/FocuSee/Camtasia all ship it; complements the existing 16:9 quality grid.)

### Design
- `exportDimensions.ts`: add `ExportCanvas = "original" | "9:16" | "1:1" | "4:5"` (default `original`). For non-original: fit the *height* (or width for 9:16 from portrait sources) per the quality scale, then **center-crop** the other axis — crop math reuses the even-normalization approach in `calculateMp4ExportDimensions` L87. Keep `calculateMp4SourceDimensions` untouched.
- Crop focus: center by default; if a `ZoomRegion` is active at export time the existing focus logic already reframes — canvas crop composes AFTER zoom (document this order in code comments).
- UI: segmented canvas picker in `ExportSettingsMenu` next to the quality grid, with live dimension readout (the grid already shows `mp4OutputDimensions` — extend it).
- Both routes: native static-layout args take explicit scale/crop (the `fps=…,scale=…` args at native-video.ts L1161 area + per-backend builders); WebCodecs crops in the frame renderer canvas draw — add the canvas rect to `ExportSettings` and honor it in `frameRenderer`/`modernFrameRenderer`.
- Persistence: `exportCanvas` in `ProjectEditorState` (pattern: `exportQuality`).
- GIF path: apply the same canvas crop in `gifExporter` sizing (`GIF_SIZE_PRESETS` interacts — canvas applies first, then size preset).

### Tests
- `exportDimensions.test.ts`: canvas×quality matrix (even dims, center-crop correctness, portrait source + 9:16 passthrough).
- Frame renderer test: canvas crop offset math.
- Persistence round-trip for `exportCanvas`.

### i18n
`canvasOriginal`, `canvasVertical`, `canvasSquare`, `canvasPortrait` — ×11.
